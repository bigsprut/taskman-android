## Q1. Compose: оставить BOM 2026.09.00 или поднять compileSdk до 37.1?

**Контекст.** ТЗ §5.1 фиксирует `compileSdk = targetSdk = 37`. Свежий стабильный Compose
(BOM 2026.11.01, Compose UI 1.13.0) на этапе `checkDebugAarMetadata` требует компиляционный
SDK **37.1**; в установленном SDK платформа одна — `android-37.0`.

**Что сделано.** Взята последняя пара, собирающаяся с SDK 37: BOM **2026.09.00**
(Compose UI 1.12.1, Material 3 1.4.0). Сборка и тесты зелёные, приложение проверено на эмуляторе
API 37.

**Варианты.** (а) оставить как есть — строго по ТЗ; (б) поднять `compileSdk` до 37.1
(платформы 37.1 в SDK нет, её нужно доставить) и обновиться на BOM 2026.11.01.

**Нужно решение:** до приёмки, потому что от этого зависит версия Compose в PR.

## Ф1 — вопросы к мейнтейнеру

### Q6. Подтвердить на живом сервере поведение `completed_at` при смене статуса

Приложение ставит статус чекбоксом через `POST /api/tasks` (UPSERT полного объекта + CAS) и
**не передаёт** `completed_at` — по эталонной фикстуре и по моку сервер сам проставляет дату
завершения и пишет историю (`completed_at` = ts последней записи истории). На моке проверено:
`completed_at` заполнился. Просьба подтвердить на проде — если сервер этого не делает,
клиент начнёт передавать `status_date`/`completed_at` явно (правка в `TaskPayload`, одна строка).

### Q7. `status_date` в Ф1 не передаём — ок?

По ТЗ §4 «без необходимости `status_date` не слать — сдвигает даты». Чекбокс меняет только
статус, дату статуса не трогаем. «Выполнена задним числом» — это Ф2.

### Q8. Идемпотентность `DELETE` для Ф4

Повторный `DELETE /api/tasks/{id}` сейчас отдаёт 404 (и на моке, и по контракту). Клиент
переживает — показывает код. Для очереди ретраев в Ф4 идемпотентный `200 {"deleted": id}`
был бы проще. Решение за владельцем, на Ф1 не влияет.

### Q9. Фильтр по статусу и подзадачи — подтвердить трактовку

Выбрано: фильтр статуса отбирает **только родителей**, подзадачи показываются всегда
(иначе `▸ 3/3` под «Активные» раскрывался в пустоту). Если ожидалось иное поведение —
скажи, поправлю вместе с тестами.## Ф2 — вопросы к мейнтейнеру

### Q10. `completed_at` при правке «задним числом»

Клиент передаёт `status_date` (он уходит в историю — проверено: `completed@10.11.2026`), но
`completed_at` сервер ставит текущим моментом. Пользователь этого не видит (список сортируется
по истории), но в PWA/отчётах дата завершения будет «сегодня». Варианты: (а) сервер ставит
`completed_at = status_date` при смене статуса; (б) клиент сам передаёт `completed_at` — одна
строка в `TaskPayload.fromDraft`. Что выбираем?

### Q11. Создание задачи верхнего уровня

В Ф2 редактор открывается только для существующих задач; новые создаются лишь как подзадачи
(по §5.3-Ф2 большего не требуется). До Ф5 в приложении нет способа завести задачу — это
ожидаемо, или добавить кнопку «+» уже сейчас (тот же лист с пустым черновиком)?

### Q12. `Espresso 3.8.0-alpha04` ради API 37

Instrumented-тесты на Android 17 падают с Espresso 3.7 (`InputManager.getInstance` удалён).
Подключена ветка 3.8.0-alpha04 **только в `androidTest`**. Ок, или предпочитаешь держаться
стабильных версий и тогда UI-регресс будет запускаться на API ≤36?

### Q13. Markdown: границы поддержки

Поддержано: параграфы, заголовки, списки (плоские), цитаты, код, инлайн-разметка, ссылки.
Не поддержано: вложенные списки (схлопываются в один уровень), таблицы, HTML, картинки
(рисуется alt-текст). Для Ф2 считаем достаточным?
## Ф3 — вопросы к мейнтейнеру

### Q14. `updated_at` задачи при аплоаде вложения

На моке версия задачи при добавлении вложения не меняется. Если живой сервер её поднимает,
это влияет на CAS-сценарии: клиент после успешной мутации делает `refresh()`, поэтому версия
подтянется, но хотелось бы знать фактическое поведение.

### Q15. Шаринг файла без права чтения

Если отправитель не выдал `FLAG_GRANT_READ_URI_PERMISSION` (или файл уже удалён), чтение
`content://` падает, и сейчас показывается «Не удалось приложить файлы: внутренняя ошибка».
Сделать для этого отдельное сообщение («нет доступа к файлу, попробуйте отправить заново»)?

### Q16. Лимит размера вложения

Клиент читает выбранный файл целиком в память и не знает серверный лимит. Показывать ли
в UI ориентир (например, «до 8 МБ»), если сервер этот лимит документирует в контракте?

### Q17. Полноэкранный просмотр картинок

Сейчас превью — только в строке вложения, открытие — внешним приложением (по §5.3-Ф3 хватает).
Нужен ли внутренний полноэкранный просмотр (Coil, свайп между картинками) — это отдельный объём.
## Ф4 — вопросы к мейнтейнеру

### Q18. Кнопка «отправить сейчас»

Очередь отправляется сама: при возврате в приложение, по возвращению сети и воркером с backoff.
Нужна ли в баннере «Не отправлено изменений: N» кнопка ручной отправки, или автоматики достаточно?

### Q19. Буферизация аплоада вложений

Сейчас вложения и сотрудники отправляются только при наличии сети (сетевой сбой — сообщение,
в очередь не копится). Буферизовать аплоад (копировать байты файла в очередь) — отдельный объём
работы; нужно ли это до появления требований, или оставить как есть?

### Техдолг, зафиксированный по итогам Ф3/Ф4

- **Стриминг-аплоад** вместо чтения файла целиком в память (ответ Q16) — риск OOM на больших
  файлах; не блокирует, предлагаю взять в Ф5 по остатку.
- Ориентир лимита размера вложения в UI — только если лимит появится в контракте сервера.
