# PHASE-REPORT — Ф7: фикс ложных 409 «задачу изменили на другом устройстве»

Ветка: `phase/7-conflict-fix` (от `main` после цветокода статусов) · Причина: багрепорт
владельца 20.11 03:08 (3× `POST /api/tasks` → 409 за минуту с одного устройства)

Итог: после собственной мутации клиент теперь применяет `updated_at` из ответа сервера;
409 с «нашей» версией обрабатывается молча (refresh + один повтор), чужой конфликт виден
прямо в редакторе; автосейв без изменений полей не ходит в сеть. Ложные конфликты
«сам с собой» ушли.

## 1. Диагноз

1. `POST /api/tasks` возвращает `{saved: [{id, updated_at}]}`, но клиент версию **игнорировал**.
2. Следующая мутация собирала payload из старой версии: автосейв редактора брал `updated_at`
   из черновика, загруженного при открытии листа; очередь — из записи с `baseUpdatedAt`.
3. Итог: собственный upsert ловил 409 и UI показывал «задачу изменили на другом устройстве».
4. Дополнительно: автосейв отправлял upsert, даже когда поля не менялись, — лишний повод
   для конфликта и трафика.

## 2. Что сделано

| Блок | Результат | Ключевые файлы |
|---|---|---|
| Версия из ответа | `acceptServerVersions()` разбирает `saved[]`, пишет `updated_at` в Room и запоминает в `acknowledgedVersions`; `latestVersion()` для черновика редактора | `data/repo/TaskMutationRepository.kt`, `LocalTaskWriter.kt`, `data/local/StateDao.kt` |
| Тихий повтор 409 | если `actual_updated_at` совпадает (допуск 1e-6) с нашей подтверждённой версией → `refresh()` + ровно одна повторная отправка с `actual`; иначе — `Conflict` | `TaskMutationRepository.flush()` |
| No-op автосейв | `saveDraft()` сравнивает поля/теги/`status_date` с локальной сущностью и при отсутствии правок возвращает `Success` без запроса | `TaskMutationRepository.saveDraft()` |
| Версия в черновике | после успешного сохранения черновик получает `updated_at` из `latestVersion()` | `ui/editor/TaskEditorViewModel.kt` |
| Видимый конфликт | баннер внутри листа редактора «Задачу изменили на другом устройстве…» + кнопка «Обновить» (перечитывает снапшот, осознанно отбрасывая черновик) — снекбар за модальным листом не виден | `TaskEditorSheet.kt`, `TaskEditorViewModel.kt` |
| Тесты | **18** новых: регресс «вторая мутация с версией из ответа», тихий повтор, чужой конфликт, no-op, точность версии | `app/src/test/**` |

## 3. Решения

1. **Отдельная карта подтверждённых версий** (`acknowledgedVersions`), а не сравнение со
   снапшотом: снапшот мог не успеть перечитаться, и тогда собственный 409 не отличить от
   чужого. В карту попадают только версии из ответов на **наши** мутации.
2. **Допуск 1e-6 при сравнении версий**: unix-время приходит float; точное равенство double
   после разных путей сериализации — лишний риск (на живой проверке PowerShell вообще потерял
   точность при ручном upsert через curl — это артефакт инструмента, не клиента).
3. **Ровно один тихий повтор**: повторный 409 — уже реальное расхождение, показываем конфликт
   без бесконечных циклов.
4. **Конфликт в редакторе — баннером внутри листа**: `SnackbarHost` находится под
   `ModalBottomSheet`, поэтому сообщение о конфликте в открытом редакторе раньше было
   невидимым. Кнопка «Обновить» — осознанный выбор пользователя, а не тихая потеря правок.
5. **`/toggle` не используется**: чекбокс ходит через UPSERT (§5.3-Ф1), поэтому требование
   «обновлять версию из ответа toggle» закрывается тем же механизмом; отдельного вызова
   `/toggle` в клиенте нет.

## 5. Ограничения

- Если после конфликта пользователь не нажмёт «Обновить», а продолжит править — баннер
  сбрасывается при первой же правке, но версия в черновике остаётся старой, и следующее
  сохранение снова даст конфликт (не перезапись). Осознанный выбор: молча ничего не сливаем.
- Прямой VM-тест «после успешного close() в черновик попадает версия из ответа» не писался:
  репозиторный уровень покрыт (`latestVersion` + применение версии), существующие
  `TaskEditorViewModelTest` зелёные. Вопрос Q25 — нужен ли отдельный VM-тест.
- Повторная отправка при сетевом сбое **после** тихого повтора не пинована тестом: запись
  остаётся в очереди (исход `Queued`), это существующее поведение Ф4.

## 6. Server (§7)

Сервер не менялся; его контракт (CAS `updated_at`, `409 + actual_updated_at`,
`saved[].updated_at`) — источник истины. Багрепорт серверу не нужен: дефект был на клиенте.
Замечание на будущее: если сервер когда-нибудь начнёт менять `updated_at` при аплоаде
вложения (Q14 из Ф3), клиенту это не помешает — версия обновится ближайшим `refresh()`.
