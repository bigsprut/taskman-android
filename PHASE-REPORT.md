когда связь вернулась, без дублей; сервер-отказ (4xx) не копится; 409 показывает явный конфликт.

## 2. Решения фазы

1. **Одна запись очереди на задачу.** Повторные правки схлопываются: очередь не растёт от
   каждого нажатия, а сервер получает последнюю полную версию. `baseUpdatedAt` фиксируется при
   **первой** правке и подставляется в payload — иначе после первой успешной отправки следующая
   получила бы ложный 409.
2. **Сервер-отказ не копится.** Любой 4xx снимает запись из очереди и отдаётся в UI точной
   причиной; состояние перечитывается с сервера, поэтому оптимистичная правка исчезает, если
   сервер её отверг.
3. **401/403 `device` оставляют запись** — после входа/подтверждения устройства её отправит
   воркер; навигацию уводят существующие события сессии.
4. **Очередь буферизует только мутации задач** (upsert/delete/переименование подзадачи).
   Аплоад вложений и CRUD сотрудников не буферизуются: `content://` может стать недоступным,
   а сотрудники без сети — редкий сценарий. Новые подзадачи тоже не копятся: `id` выдаёт сервер.
5. **WorkManager.** Разовая отправка с сетевым ограничением, backoff 30 с, `KEEP` (очередь
   сериализована внутри репозитория), плюс отправка из `onResume` и по возвращению сети — так
   очередь уходит сразу, а не через backoff. Периодическое обновление — раз в 15 минут
   (§5.4: не чаще раза в 15 минут), дешёвое благодаря `ETag`/304.
6. **Миграция обязательна.** С Ф4 в базе живут данные, которых нет на сервере (очередь),
   поэтому деструктивный fallback убран: v1→v2 создаёт таблицу и не трогает снапшот.

## 4. Известные мелочи (техдолг, из `ANSWERS-F3.md`)

1. **Стриминг-аплоад** (Q16): файл читается в память целиком — риск OOM на очень больших
   файлах. Не блокирует Ф4, взять в Ф5 по остатку.
2. Аплоад вложений и CRUD сотрудников не буферизуются (см. §2 п.4) — осознанное ограничение.
3. Параметр `TaskRepository.offlineQueue` и очистка очереди при выходе покрыты кодом, но без
   отдельного теста (поведение тривиально: `queue.clear()` в `clearLocalData`).

## 6. Server (§7)

Сервер не менялся, контракт не нарушен. Для Ф4 достаточно существующего CAS `updated_at`
и `DELETE`/`POST /api/tasks`. Из Ф2 остаётся рекомендация: идемпотентный `DELETE` (200 на
повтор) сделал бы ретраи очереди безопаснее — сейчас повторный DELETE даёт 404, а он
обрабатывается как сервер-отказ (запись снимается).
