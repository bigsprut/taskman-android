# ТЗ-01: Нативное Android-приложение «Задачи» (клиент taskman)

Версия 1.1 (public) · 19.11.2026 · Владелец: bigsprut

Нативный Android-клиент (Kotlin + Jetpack Compose) к существующему
self-hosted бэкенду taskman (FastAPI + SQLite). Бэкенд и PWA-клиент работают
в проде; это — только нативный клиент. Трек нативный: обёртка PWA отброшена —
она не лечит отзывчивость (холодный старт, скролл больших списков,
клавиатура).

---

## 1. Роли и правила игры

- **Владелец (bigsprut)**: требования, вето, живое пользование.
- **Исполнитель/контрибьютор**: код приложения. Одна фаза (или смысловая
  правка) = одна ветка → PR → ревью и приёмка мейнтейнера → merge.
- **Мейнтейнер (приёмка)**: повторяет сборку и тесты своим прогоном;
  отчёт исполнителя — не факт. Живая приёмка — на целевом устройстве.
- **Git/GitHub — единственный интерфейс**: этот репо. `main` защищён
  (только PR). Вопросы/отчёты — GitHub issues + файл `PHASE-REPORT.md`
  в корне ветки исполнителя. Бинарники «на веру» не принимаются.

## 2. Ресурсы — что УЖЕ ЕСТЬ (не создавать заново)

- **Бэкенд taskman**: self-hosted FastAPI + SQLite за HTTPS. Полный
  API-контракт — раздел 6, менять сервер в этом репо нельзя (раздел 7).
- **Эталонная фикстура**: `fixtures/api/state.sample.json` — реальный ответ
  `GET /api/state` (51 задача, 3 статуса из 4, подзадачи, теги, вложения,
  история статусов), санитизированный от личных данных. Эталон парсера и
  тестов. Менять запрещено (раздел 7).
- **Целевое устройство**: OnePlus 15 (CPH2747), **Android 17, API 37**,
  ColorOS 17. Приёмка на живом устройстве — мейнтейнер.
- Подключение: base URL и токен передаются на входе приложения (раздел 5.4);
  доступ к чужому прод-инстансу не выдаётся.

## 3. Чего НЕТ + правило

Нет в списке раздела 2 — это НЕ вывод «не существует». Нужен ресурс
(облако, CI, платная библиотека, Firebase и т.п.) — сначала вопрос в issue.
Любая покупка — только с обоснованием (цена + эффект + почему бесплатно
нельзя), решение за владельцем. По умолчанию бюджет **$0**: без платных
зависимостей, облачных сервисов, краш-аналитики. Регистрации аккаунтов
от имени владельца запрещены.

## 4. Проверенные факты о сервере (живьём, не пересматривать)

- Авторизация: заголовок **`Token: <строка>`** на все `/api/*` (именно
  «Token», НЕ «X-Token»).
- **Версионность (CAS)**: POST /api/tasks принимает `updated_at` —
  ожидаемая версия задачи из последнего `/api/state`. Расхождение →
  `409 {"error":"conflict","actual_updated_at":…}` — другой клиент правил
  задачу. Нативный клиент ОБЯЗАН: слать updated_at при каждом upsert и
  обрабатывать 409 = пере-fetch state + показать конфликт (не перезаписывать
  молча).
- **gzip + ETag/304**: `/api/state` отдаёт `ETag` (md5 данных без
  server_time) и уважает `If-None-Match` → 304 без тела. OkHttp с
  включённым `Cache` делает это прозрачно; повторный poll без изменений =
  0 байт.
- Привязка устройства (TOFU): клиент генерирует UUID, шлёт заголовком
  `X-Device-Id` на все `/api/*`. Незнакомое устройство при валидном токене
  получает `403 {"error": "device"}` и попадает в pending; автоподтверждение
  на сервере ≤30 с. Приложение переживает интервал: экран «устройство ждёт
  подтверждения» + автоповтор `/api/state` раз в 30 с.
- `GET /api/attachments/{id}` — токен ТОЛЬКО query-параметром `?token=…`
  (заголовок этот эндпоинт не читает). Остальные `/api/*` — заголовком.
- POST `/api/tasks` — **UPSERT полного объекта**: что не передано —
  перезапишется значением по умолчанию. payload обязан содержать ВСЕ поля
  задачи. Поле `tags` = список id, полностью заменяет набор.
- `id: null` = новая задача (сработает категория по умолчанию из settings).
  Статусы: `created | inprogress | completed | canceled` (легаси
  `needsAction` принимается как `created`).
- История статусов пишется только при смене статуса или явном `status_date`;
  без необходимости `status_date` не слать (сдвигает даты).
- Времена — unix-float СЕКУНДЫ (`1765843200.123`), не миллисекунды.
- DELETE задачи — soft-delete поддерева подзадач одним вызовом.
- Multipart-аплоад: поле формы обязано называться `file`.
- Один пользователь (single-user): никаких экранов регистрации; токен
  вводится один раз и хранится в устройстве.

## 5. Требования к приложению

### 5.1. Стек и каркас (стандарты Android)

- Kotlin 2.x, **Jetpack Compose + Material 3** (BOM актуальный стабильный),
  single-module `:app`.
- `compileSdk = targetSdk = 37` (Android 17); `minSdk = 26`. AGP/Gradle —
  актуальные стабильные; версии зафиксировать в Ф0 с результатом сборки.
- Сеть: Retrofit + OkHttp + kotlinx.serialization. Картинки: Coil.
  Локальный кэш/офлайн: Room. Настройки/токен: DataStore (+ключ в Android
  Keystore). Фоновая очередь: WorkManager. DI: manual или Hilt — обосновать
  в PR Ф0. Новые зависимости — с обоснованием в PR (раздел 3).
- `package name`: **`io.github.bigsprut.taskman`** — нейтральный, не менять
  без решения владельца (package name — вечный идентификатор инстанса).

### 5.2. Дизайн-стандарты (Material 3, обязательны)

- **Тема**: Material 3, dynamic color на API≥31, фолбэк — своя схема.
  Тёмная и светлая темы, первый кадр не мигает белым в тёмной. Только
  `WindowInsets.safeDrawing/navigationBars` (никаких магических dp-резервов).
  Edge-to-edge включён.
- **Каркас**: экраны в `Scaffold` c `TopAppBar`; снекбары через Scaffold
  host. Внизу — NavigationBar (Список / Настройки-справочники).
- **Жесты**: удаление задачи — M3 `SwipeToDismissBox` (влево, с диалогом
  подтверждения). Системный **predictive back** включён
  (`android:enableOnBackInvokedCallback="true"`). Скролл — `LazyColumn` со
  стабильными ключами (id задачи), не index.
- **Иконка**: adaptive icon (фон + foreground + monochrome слой). Splash —
  core-splashscreen.
- **Типографика/доступность**: шкала M3 (без голых `fontSize`), тач-таргеты
  ≥48dp, `contentDescription` на иконках, font-scale 130% без развала.
- **Состояния экрана**: Loading/Empty/Error/Auth-Device раздельны
  («нет данных» ≠ «нет сети» ≠ «устройство не подтверждено»), с «Повторить».

### 5.3. Функциональность (срез MVP по фазам)

UI-политика продукта: в списке задач НЕТ кнопок удаления (только
смахивание); у групп чипов-фильтров обязательны читаемые подписи; цветной
текст на залитом фоне — авто-контраст по яркости; сортировка ≠ фильтр.

- **Ф0. Каркас + вход + список (read-only)**: экран входа (base URL +
  токен), привязка устройства (UUID в DataStore, экран ожидания),
  `/api/state` → Room → список с сортировкой `STATUS_ORDER: inprogress →
  created → completed → canceled` (активные вперёд), внутри группы —
  свежесть даты статуса. Свайп вниз — обновление.
- **Ф1. Список в полный рост**: фильтры (статусы: «Активные» по умолчанию =
  created+inprogress, Выполнена, Отменена, Все; категории; теги), счётчики,
  подзадачи сворачиваемые (▸ N/M), чекбокс = Выполнена↔Создана,
  смахивание-удаление, бейджи статуса/тегов/вложений/сотрудника.
  **Блок фильтров — СКРЫВАЕМЫЙ** (решение владельца 20.11): компактная
  строка-переключатель (например «Отборы ▾» со счётчиком активных фильтров);
  развёрнутые фильтры занимают экран и мешают списку — сворачивание
  освобождает место под задачи; состояние (свёрнуто/развёрнуто) сохраняется
  между запусками.
- **Ф2. Редактор задачи** (bottom-sheet): все поля — название, описание
  (markdown: ввод plain, просмотр отрендеренным — библиотеку обосновать),
  статус + дата статуса (задним числом) + «История», категория, теги
  (чипы), сотрудник — **выбор из СПИСКА (dropdown/ bottom-sheet-лист
  с поиском), НЕ чипами-кнопками: справочник сотрудников может быть
  большим** (решение владельца 20.11), дата создания. Подзадачи: добавить,
  переименовать (инлайн), галка, удалить. Закрытие листа ЛЮБЫМ путём =
  автосохранение. Регресс: несохранённые поля НЕ теряются при действии с
  вложениями/подзадачами при открытом редакторе (сохранять модель листа
  атомарно). В списке задач — явное средство СОЗДАНИЯ задачи (FAB «+»
  или поле сверху), не только чтение.
- **Ф3. Вложения**: аплоад multipart (photo picker + «Поделиться в Задачи» =
  ACTION_SEND/SEND_MULTI intent-filter), превью картинок (Coil, `?token=`),
  открытие PDF/файлов внешним просмотрщиком (FileProvider), share наружу,
  удаление. Сотрудники (справочник): CRUD на экране настроек.
- **Ф4. Офлайн**: Room — единственный источник UI-правды (offline-first),
  очередь мутаций (WorkManager, backoff). В очередь — ТОЛЬКО сетевые сбои
  (IOException); сервер-отказ (4xx) НЕ копится — тост с точной причиной
  («сервер отказал: 403», «устройство не подтверждено»). Конфликты — через
  CAS `updated_at` (см. §4): 409 → рефetch + явный конфликт в UI.
- **Ф5. Справочники и настройки**: теги и категории CRUD (цвет), категория
  по умолчанию, порядок сортировки, экспорт задач текстом (markdown).
  Пуши, виджеты, мультиюзер — НЕ в MVP.

### 5.4. Нефункциональные

- Холодный старт < 1.5 с на целевом устройстве; 50+ задач скроллится без
  дёрганий.
- Батарея: фоновая синхронизация не чаще раза в 15 мин и только при
  изменениях; вложения грузить лениво.
- Все строки UI — русский (исходный язык продукта); вынос в strings.xml.
- Токен и URL — НИКОГДА в git/логах/crash-выводе. Токен — DataStore+Keystore;
  base URL — из `local.properties` (gitignored) в BuildConfig, в репо —
  placeholder (`https://example.com:8444`).

## 6. API-контракт (проверено живьём, 11.2026)

Base: `https://<host>:<port>` (из local.properties, НЕ хардкодить).
Все запросы: заголовок `Token: <token>` + `X-Device-Id: <uuid>`; тело —
JSON, кроме аплоада. Фикстура полного состояния: `fixtures/api/state.sample.json`.

| Метод | Путь | Тело → Ответ |
|---|---|---|
| GET | `/api/state` | → `{lists[], categories[], employees[], tags[], tasks[], settings{}, server_time}`; task: `{id, list_id, parent_id\|null, category_id\|null, title, content, status, source\|null, created_at, updated_at, completed_at\|null, deleted, tags[id], attachments[{id, task_id, orig_name, mime, size, created_at, deleted}], history[{status, ts}]}`. Заголовок `ETag`; `If-None-Match` → 304 |
| POST | `/api/tasks` | `[TaskIn] → {saved[{id, updated_at}], server_time}`; TaskIn: `{id\|null, list_id, parent_id\|null, category_id\|null, title, content, status, source\|null, tags[], created_at\|null, completed_at\|null, status_date\|null, updated_at\|null(CAS)}`. **UPSERT полного объекта**; несовпавший `updated_at` → 409 |
| POST | `/api/tasks/{id}/toggle` | `{status} → {id, status, updated_at}` |
| DELETE | `/api/tasks/{id}` | → `{deleted: id}` (soft-delete поддерева) |
| POST | `/api/tasks/{id}/attachments` | multipart поле `file` → `{id, name, size}` |
| GET | `/api/attachments/{id}?token=…` | файл inline (токен только query!) |
| DELETE | `/api/attachments/{id}` | → `{deleted: id}` |
| GET/POST/PATCH/DELETE | `/api/tags[/{id}]` | `{title, color}` / `{title?\|null, color?\|null}` |
| POST/PATCH/DELETE | `/api/categories[/{id}]` | `{title, color}` / `{title?, color?}` |
| POST | `/api/lists` | `{title} → {id, title}` |
| POST/PATCH/DELETE | `/api/employees[/{id}]` | `{name}` |
| PATCH | `/api/settings` | `{default_category: id\|null}` |

Ошибки: `401` → экран входа; `403 {"error":"device"}` → экран ожидания
подтверждения (автоповтор 30 с); `409` → конфликт версий задачи; прочие
4xx — тост с кодом.

Контракт описывает ФАКТИЧЕСКОЕ поведение сервера, включая известные
шероховатости. Нашёл расхождение — это багрепорт (issue), а не повод
молча подгонять клиент.

## 7. Что НЕ делать — и что ОБЯЗАТЕЛЬНО с серверной частью

**Стандарт продукта: ПРОД, не тест и не учебная разработка.** Аргумент
«личное приложение / один пользователь — и так сойдёт» запрещён наравне с
любым срезанием стандартов Android, безопасности и качества. Отступление от
стандарта — только через issue с явным одобрением владельца.

Серверная часть разрабатывается и деплоится владельцем: PR с правками
сервера в это репо не принимаются — но это НЕ значит «молча пользоваться
багованным сервером»:

- **Багрепорт обязателен** при любом расхождении контракта (§6) с фактическим
  поведением: issue с воспроизведением (HTTP-метод, путь, тела, код ответа)
  и оценкой влияния на клиент. Молчаливая подгонка клиента под баг =
  дефект приёмки.
- **Рекомендации по улучшению сервера приветствуются — от точечных до
  глобальных архитектурных** (delta-sync, пуши, версионность). Формат:
  что не так / какой риск закрывает / цена / план миграции без простоя
  живых клиентов. Готовый дифф/псевдокод приветствуется.
- **Блокирующий баг — не обходить молчаливым костылём**: issue-эскалация;
  решение «чиним сервер vs обход в клиенте» принимает владелец.
- Фикстуры `fixtures/` не менять.
- Не добавлять: аналитику, краш-репортеры, рекламу, авто-обновления.
- Секреты: токен/URL не в коде, не в коммитах, не в логах.
- Не выдумывать ограничения сверх ТЗ; непонятное — issue.

## 8. Порядок работы

1. Форк или ветка `phase/N-<slug>` / `feature/<slug>`.
2. Исполнитель берёт фазу строго по порядку Ф0→Ф5 (или отдельный issue),
   пишет целиком, сам нарезая подзадачи «кусок, понятный за один вход в
   контекст». По завершении: PR + `PHASE-REPORT.md` в корне ветки (что
   сделано, версии зависимостей, результат `gradlew test assembleDebug`,
   число тестов из `app/build/test-results`).
3. Приёмка: skim диффа → свой прогон сборки/тестов → живая приёмка на
   устройстве по критериям фазы → merge. Багрепорты — одной пачкой в
   review-комментарии PR.
4. Коммиты документов — только в main, через PR.
5. ГРАБЛИ:
   - `gradlew` exec-бит теряется при пуше с NTFS — не «чинить» правкой
     файла, мейнтейнер выставит бит сам.
   - НЕ выдумывать `X-Device-Id` при тестах против общего сервера: любой
     id привязывается навсегда (TOFU). Тестовый UUID — свой постоянный,
     вне git.
   - Разработка и эмулятор — против локального стенда (мок на фикстуре)
     или своего инстанса сервера; доступ к приёмочному устройству —
     только через мейнтейнера.

## 9. Критерии приёмки по фазам

- **Ф0**: APK собирается одной командой из чистого клона; вход с реальным
  токеном; экран ожидания device-подтверждения переживает 403 и сам
  разворачивается в список; список = фикстурному набору (50+ строк,
  сортировка STATUS_ORDER); тёмная/светлая тема, поворот, predictive back —
  без развалов.
- **Ф1**: фильтры/счётчики/подзадачи/чекбокс/удаление свайпом — по §5.3-Ф1;
  мутации долетают до сервера; тест-записи с префиксом `__ТЕСТ` — создавать
  и вычищать в одном прогоне.
- **Ф2**: правка каждого поля сохраняется и переживает переоткрытие листа и
  убивание процесса; кейс «несохранённые поля + действие с вложением/
  подзадачей → поля на месте» — обязательный регрессионный тест UI.
- **Ф3**: картинка из галереи и «Поделиться» из другого приложения долетают
  и видны в существующих клиентах; PDF открывается внешним просмотрщиком;
  удаление вложения чистит и сервер.
- **Ф4**: самолёт-режим: чтение работает, мутации копятся, тосты точные;
  сеть вернулась — очередь улетает без дублей; сервер-отказ НЕ копится;
  409-конфликт показан явно.
- **Ф5**: CRUD тегов/категорий отражается в `/api/state`; экспорт —
  корректный markdown по фикстуре.

Каждая фаза = проверяемый результат или честный блокер в issue. «Почти
готово» = не готово.
