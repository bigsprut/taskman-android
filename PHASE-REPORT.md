# PHASE-REPORT — Ф0: каркас + вход + список (read-only)

Ветка: `phase/0-skeleton` · Основание: `TZ-01-android-app.md` (§5.1–5.4, §6, §7, §9-Ф0)
· План: `PLAN.md` · Нарезка подзадач: `TASKS.md`

Итог: APK собирается одной командой из чистого состояния, вход по токену работает, экран
ожидания устройства переживает 403 и сам разворачивается в список, список = набору фикстуры
(51 задача) в порядке `STATUS_ORDER`. Проверено не только тестами: приложение прогнано на
эмуляторе Android 17 (API 37).

  точка категории использует цвет с сервера;
- настройки: адрес, device-id, копирование в буфер, версия, «Сменить сервер и токен»;
- тёмная тема, поворот в landscape, отсутствие крэшей в logcat — без развалов;
- гонялся против локального мока на фикстуре (`tools/mock-server`), живой сервер и приёмочное

## 5. Решения, которые стоит знать (обоснования)

1. **Manual DI вместо Hilt.** Один модуль, ≤6 зависимостей — Hilt даёт лишний
   аннотационный процессор и сборочную магию; граф явный в `di/AppContainer.kt`. Если к Ф4
   он вырастет, переход на Hilt — отдельный PR.
2. **Свой конвертер Retrofit на kotlinx.serialization** (`KotlinxJsonConverterFactory`)
   вместо `converter-kotlinx-serialization`: бюджет $0, одна конфигурация `Json` на клиент
   и на тесты.
3. **Сортировка в Kotlin-компараторе, не в SQL.** Одна реализация, покрытая JVM-тестом;
   при 50–1000 задачах стоимость пренебрежима. SQL-сортировка появится, только если это
   станет узким местом.
4. **Room — источник UI-правды уже в Ф0.** Список показывается из кэша сразу, сеть лишь
   обновляет снапшот: это фундамент Ф4 (offline-first) и заодно выполняет «холодный старт
   < 1.5 с» (UI не ждёт сети).
5. **Base URL подставляет интерсептор**, Retrofit создаётся на заглушке: адрес вводится
   пользователем и меняется без перезапуска процесса.
6. **Непроверенный токен не сохраняется.** Токен живёт в памяти до подтверждения сервером
   (`/api/state` 200 или 403 `device`), только потом попадает в DataStore в шифротексте.
7. **Деструктивная миграция Room** (`fallbackToDestructiveMigration`) допустима только в Ф0:
   база — кэш серверного снапшота. С Ф4 (локальные мутации) обязательны настоящие миграции —
   это зафиксировано комментарием в `TaskmanDatabase`.
8. **`server_time` как признак полноценного снапшота.** Ответ 2xx без `server_time` не
   заменяет кэш: прокси/баг, вернувший `200 {}`, не должен превращать список в «пусто».
9. **Почему Compose BOM 2026.09.00, а не свежий 2026.11.01.** Compose 1.13.0 требует
   компиляционного SDK 37.1, а ТЗ фиксирует `compileSdk = 37` (в SDK установлена платформа
   `android-37.0`). Взят последний стабильный набор, собирающийся с SDK 37: UI 1.12.1 /
   M3 1.4.0. Поднятие до 1.13 — отдельное решение владельца (см. §9, вопрос 1).

## 6. server — наблюдения и рекомендации (ТЗ §7)

Контракт §6 расхождений с фактическим поведением **не дал**: 401/403 `device`, gzip, ETag,
формат полей, `deleted` 0/1, unix-секунды — всё как описано. Ниже — то, что стоит улучшить
на сервере; сервер в этом PR не менялся.

1. **`ETag` без `Cache-Control` не кэшируется.** OkHttp сохраняет ответ для повторной
   валидации, только если сервер разрешил кэширование. Сейчас прозрачные 304 зависят от
   заголовков: если `Cache-Control` не приходит, клиент каждый poll тянет полное тело.
   *Рекомендация:* отдавать `ETag` вместе с `Cache-Control: no-cache` (значение «хранить, но
   ревалидировать») — тогда §4 («повторный poll без изменений = 0 байт») выполняется всегда.
   *Цена:* одна строка в ответе; миграция не нужна.
2. **`server_time` — обязательное поле.** Клиент использует его как маркер полноценного
   снапшота. Просьба не убирать и не делать `null` в штатных ответах (сейчас так и есть).
3. **403 `device`: полезно отдавать `retry_after`.** Экран ожидания сам повторяет раз в 30 с
   (по ТЗ), но если сервер знает точнее (например, «подтверждение раз в 10 с»), это
   сократит ожидание. *Цена:* одно поле в теле 403; обратно совместимо.
4. **`task.source` — имя сотрудника строкой, а не id.** При переименовании сотрудника
   историческая связь теряется, а клиенту приходится сопоставлять по имени. *Рекомендация:*
   добавить `employee_id` рядом с `source` (клиент покажет имя из справочника).
   *Цена:* аддитивное поле/колонка; старые клиенты игнорируют.
5. **Токен в query для вложений (`?token=`) попадает в логи прокси/браузера.** Для Ф3 это
   учтено (документируем и не логируем), но безопаснее поддержать `Authorization`/`Token`
   заголовком на `/api/attachments/{id}` или одноразовые подписанные ссылки.
6. **Глобально (Ф4+): delta-sync.** Полный `/api/state` на каждый poll — O(данных).
   `GET /api/state?since=<server_time>` c удалениями-маркерами убрал бы 90% трафика и
   упростил конфликты. *Цена:* серверная версионность; план миграции — по фазе.

## 7. Ограничения Ф0 (сознательно, это следующие фазы)

- Нет мутаций: чекбокс, переименование, удаление, редактор, вложения, фильтры — Ф1–Ф3.
- Нет офлайн-очереди: при отсутствии сети показывается кэш + баннер; повтор — вручную
  (pull-to-refresh) или автоповтором на экране ожидания. Очередь мутаций — Ф4.
- Coil/WorkManager в зависимости не добавлены: в Ф0 не используются (появятся в Ф3/Ф4).
- Обработка 409 (`Conflict`) уже классифицирована и покрыта тестом, но полноценный UX
  конфликта (рефетч + явное сообщение) — Ф1/Ф4, потому что в Ф0 нет мутаций.
- Room: деструктивная миграция (см. §5.7).

## 8. Известные мелочи / техдолг

- `local.properties` в рабочем дереве (gitignored) указывает на локальный мок;
  в репозитории его нет, в чистом клоне подставляется placeholder из ТЗ.
- `gradlew` в git приходит с NTFS без exec-бита — по ТЗ §8 бит выставляет мейнтейнер.
- Моноширинный device-id на экране настроек переносится на две строки при 32+ символах —
  читаемо, но в Ф5 можно сделать карточку компактнее.
- `PLAN.md`/`TASKS.md` — рабочие документы фазы (нарезка и передача подзадач), не часть ТЗ.
