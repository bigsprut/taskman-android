## 2. Решения фазы (и почему так)

1. **Чекбокс идёт через `POST /api/tasks` (UPSERT полного объекта), а не `/toggle`.**
   ТЗ §4 обязывает клиент слать `updated_at` при каждом upsert и обрабатывать 409; у
   `/toggle` в контракте нет CAS, то есть конфликт нельзя даже заметить. Проверено живьём:
   параллельная правка с «другого клиента» даёт 409, приложение показывает сообщение и
   перечитывает состояние, данные сервера не перезаписываются.
2. **`completed_at` не вычисляем на клиенте.** По эталонной фикстуре сервер сам ставит дату
   завершения при смене статуса (она совпадает с ts последней записи истории). Payload
   передаёт `null`, сервер проставляет — подтверждено на моке (`completed_at` заполнился).
3. **Фильтр статуса отбирает родителей, дети показываются всегда.** Первая версия фильтровала
   и детей — на живой проверке это дало раскрытие «в пустоту»: у группы `▸ 3/3` все дети
   выполнены, и под фильтром «Активные» список детей был пуст. Дети — контекст родителя,
   `▸ N/M` — его прогресс; так поведение предсказуемо.
4. **После каждой мутации — `refresh()`.** Даты, историю и `updated_at` считает сервер;
   локальная правка «на глаз» разошлась бы с ним и сломала следующий CAS.
5. **Офлайн-очереди нет** (это Ф4): сетевой сбой — сообщение с точной причиной, без
   оптимистичного «успеха».
6. **404 при повторном `DELETE`** считаем нормальным отказом (показываем код), идемпотентность
   не выдумываем — сервер в этом PR не менялся.

## 4. Раздел «server» (ТЗ §7)

Сервер не менялся; расхождений контракта, ломающих Ф1, нет. Наблюдения:

1. **Подтвердить на живом сервере два допущения** (проверены на моке, но не на проде):
   (а) при UPSERT со сменой статуса сервер сам проставляет `completed_at` и пишет историю;
   (б) `200` с `{}` (прокси/баг) отличается от настоящего снапшота наличием `server_time` —
   клиент на этом основании кэш не стирает. Если `server_time` когда-то исчезнет, клиент
   будет считать ответ неполным.
2. **Идемпотентность `DELETE`.** Повторный `DELETE` сейчас даёт 404 — клиент это переживает,
   но идемпотентный `200 {"deleted": id}` упростил бы ретраи в Ф4.
3. **CAS и `toggle`.** У `/api/tasks/{id}/toggle` нет `updated_at`, поэтому конфликт версий
   через него не виден. Клиент использует UPSERT + CAS; если на сервере появится
   `toggle` с ожидаемой версией, его можно будет переключить на быстрый путь.
4. **`status_date` в `toggle`** (вопрос от разработки мока): по ТЗ §6 в теле только `status` —
   не добавляли.
