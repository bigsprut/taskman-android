## 2. Решения фазы

1. **Создание — FAB + быстрый диалог, а не полноценный редактор новой задачи.** ТЗ допускает
   «FAB «+» или поле сверху»; быстрый ввод названия закрывает потребность, а редактор новой
   задачи потребовал бы черновика без id (id выдаёт сервер). Остальные поля новой задачи —
   дефолты сервера: категория по умолчанию из настроек (§4), статус «Создана», первый список.
2. **Создание не буферизуется офлайн.** Как подзадачи в Ф4: `id` выдаёт сервер, локально его
   не придумать; при сетевом сбое — сообщение, очередь не растёт. Вопрос Q22.
3. **Сотрудник — вложенный `ModalBottomSheet`** (sibling листа редактора), а не dropdown:
   большой справочник требует поиска и прокрутки. Фильтр — чистая функция `filterEmployees`,
   покрыта тестами. Выбор сохраняется именем (так хранит контракт `source`).
4. **Маппинг ошибок входа — отдельная функция** `ApiFailure.toLoginError()`: 401 (и защитно
   `Http(401)`) → «неверный токен», `IOException` → «нет связи», остальное — код/неожиданный
   ответ. Это и есть исправление: раньше текст ошибки было невозможно проверить без
   DataStore/Keystore, теперь таблица закреплена 10 тестами, включая регресс «401 ≠ сеть».

## 4. Ограничения и мелочи

- **Дубли имён сотрудников** выбираются неразличимо: контракт хранит в задаче имя строкой
  (`source`), поэтому два «Ивана» в справочнике для клиента — одно значение. Вопрос Q23.
- Быстрое создание задаёт только название; остальные поля — через редактор (две операции).
- Системный диалог выбора даты статуса — на английском: это системный `DatePickerDialog`,
  локализация зависит от устройства, а не от приложения.

## 5. Вопросы (Q22–Q23)

1. **Q22** — нужно ли всё-таки буферизовать создание задачи офлайн (копировать в очередь с
   временным локальным id и сопоставлением после ответа сервера)? Сейчас — сообщение.
2. **Q23** — нужна ли защита от одинаковых имён сотрудников (например, «Иван (2)») или для
   справочника это неважно?

## 6. Server (§7)

Сервер не менялся. Наблюдение: `POST /api/tasks` с `id=null` и `category_id=null` корректно
применяет категорию по умолчанию из `settings` — так и описано в §4; поведение подтверждено
моком, на живом сервере стоит перепроверить в рамках приёмки.

## Дополнение (Ф6, итерация 2): скрываемый блок фильтров

Основание: обновлённый `TZ-01-android-app.md` §5.3-Ф1 (решение владельца 20.11) — блок
фильтров должен скрываться, состояние «свёрнуто/развёрнуто» сохраняется между запусками
(как `taskman_filtershidden` в PWA). Ветка `feature/hideable-filters` (PR после приёмки Ф6).

### Что сделано

| Блок | Результат | Ключевые файлы |
|---|---|---|
| Строка-переключатель | «Отборы» / «Отборы · N» с шевроном над списком; чипы показываются только в развёрнутом виде | `ui/list/TaskListContent.kt` |
| Счётчик отборов | `TaskFilter.activeCount()`: статус ≠ «Активные» = 1, плюс каждая категория и тег | `domain/TaskFilter.kt` |
| Персистентность | флаг `filters_hidden` в DataStore, читается при старте; свёрнутость переживает перезапуск | `data/settings/SettingsStore.kt`, `ui/list/TaskListViewModel.kt` |
| Тесты | **16** новых: `activeCount` (включая инвариант «0 ⟺ умолчание») и персистентность/переключение, включая второй экземпляр VM на том же DataStore | `app/src/test/**` |

### Решения

1. **Свёрнутость — локальная настройка устройства**, а не серверная (как порядок сортировки
   в Ф5): это предпочтение пользователя конкретного устройства.
2. **Свёрнутый блок не сбрасывает фильтры** — скрывается только видимость чипов; выбранные
   условия продолжают применяться (закреплено тестом).
3. **Счётчик считает условия, а не задачи**: пользователю важно знать, что отборы не пустые,
   когда чипов не видно.
4. **Шеврон — `KeyboardArrowDown/Up` из core-набора**: `ExpandMore/ExpandLess` доступны только
   в material-icons-extended, а ради двух стрелок тянуть зависимость не нужно.
